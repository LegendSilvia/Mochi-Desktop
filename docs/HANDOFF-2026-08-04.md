## 2. Running it on this machine (hard-won — read before `npm install`)

Two things break silently on this Windows box. Both are recorded in more detail
in the user's memory file `env-electron-install-windows`.

1. **npm 11 blocks Electron's postinstall**, so `npm install` exits 0 with no
   `electron.exe`. The warning is buried at the end of the install log.
2. **`extract-zip` then silently no-ops** — running
   `node node_modules/electron/install.js` by hand downloads and checksum-verifies
   the ~136MB zip into `%LOCALAPPDATA%\electron\Cache\`, extracts **only** the
   `locales/` folder, and **exits 0**. Re-running does nothing (cache is warm).

Fix that works — the cache is already populated at that point:

```powershell
$z = "$env:LOCALAPPDATA\electron\Cache\<hash>\electron-v<ver>-win32-x64.zip"
$d = "C:\Development\Mochi-Desktop\node_modules\electron\dist"
New-Item -ItemType Directory $d -Force | Out-Null
Set-Location $d; tar -xf $z
Set-Content "$d\..\path.txt" -Value 'electron.exe' -NoNewline -Encoding ascii
```

`path.txt` is required — `require('electron')` reads it to locate the exe.
Verify with `node -e "console.log(require('electron'))"`.
`electron.exe --version` printing nothing is **normal** on Windows (GUI
subsystem, stdout not attached).

Keep `NODE_OPTIONS=--use-system-ca` set for anything that downloads (corporate
TLS interception).

### Do not use `pkill -f electron`

It kills the user's own running Mochi instance, not just a test one. This
happened during the session. Stop background dev servers with the task tooling
instead, and check `Get-Process electron` before assuming an instance is yours.

**`@libsql/client` was an undeclared dependency.** `src/main/rag.ts:1` imports it
directly but it was absent from `package.json`. `externalizeDepsPlugin()` only
externalises *declared* dependencies, so rollup bundled it — and with it libsql's
CommonJS native loader, whose runtime `require("@libsql/win32-x64-msvc")` cannot
resolve from inside a bundle. The app threw on load. Adding it to `dependencies`
dropped the main bundle from 351 kB to 53 kB. Commit `5d67454`.

`''`. Removing the agents exposed three crashes, all fixed in the same commit:
`Agents.tsx` `create()` cloned `agents[0]` (so "New loadout" was dead at zero

### 3b. Onboarding tour + mascot sync (merged, `feat/onboarding-tour`)

Spec: `docs/superpowers/specs/2026-08-04-onboarding-tour-and-mascot-sync-design.md`
Plan: `docs/superpowers/plans/2026-08-04-onboarding-tour-and-mascot-sync.md`

**The tour** is data-driven: `src/renderer/src/state/tours.ts` defines steps; a
step with a `goto` docks the card bottom-left and locks `Next` until its

`TourLayer.tsx` interprets it; `store.tsx` owns `tour` state and performs the

**The mascot fix** had two halves. `saveState` in `src/main/ipc.ts` persisted to

broadcast to every window except the sender, guarded against echo. Separately,
`MascotLayer` returning `null` left a transparent always-on-top window covering
the work area, so `setMascotVisible()` now genuinely hides the `BrowserWindow`.
Mascot defaults to **off** on a fresh install.

## 4. In flight: the missing-replies bug (root-caused, **not** implemented)

Full write-up: **`docs/debug-missing-replies.md`** (durable copy; the original
under `.superpowers/` is now gitignored scratch and may be cleaned away).

**Symptom.** Send a message, immediately switch session or close the window →
returning shows user messages with no assistant replies.

**Root cause — two distinct defects.**

*D1 — in-flight turns are discarded.* Transcripts are written by exactly one
effect, `src/renderer/src/screens/Session.tsx:78-81`, which early-returns while
`status` is `streaming`/`submitted` and reads `messages` from the *current* chat.
`@ai-sdk/react@4.0.51` (`dist/index.js:322-327`) **constructs a brand-new `Chat`
whenever `id` changes** and drops the old one — no registry, no cache — and the
only `useEffect` in `useChat` handles `resume`, so there is no unmount cleanup and
no abort. The turn is therefore never written *and* becomes unwritable. Closing
the window is the same failure, simpler cause: there is **no**
`beforeunload`/`pagehide`/`visibilitychange` handler anywhere in `src/renderer`.

*D2 — an errored turn overwrites good history.* The guard does not early-return on
`status === 'error'`, so a failed turn **is** persisted, as a transcript
containing the user's message with no reply, replacing the previously-good one.
The reported screenshot (greeting, then two user turns, zero replies) matches an
errored turn rather than a switched-away one.

**Fix shape the user approved (not yet written):**

- Keep the settled-turn save; add a flush that fires on session-id change, on
  unmount, and on `beforeunload`, capturing the user message plus whatever
  streamed so far. Care needed: a ref shared across renders will already hold the
  *new* id by the time an id-keyed effect's cleanup runs — capture the outgoing id
  in the effect closure.
- On error, save the turn but keep the failure visible, so returning to the
  session shows something went wrong rather than a silent gap.

**Still unknown:** *why* those turns errored. That is a separate thread and is the
strongest argument for the requested debug logger — right now a failed agent call
leaves nothing to read.

## 7. Architecture notes worth knowing

- **Two renderer windows, two independent stores.** The main window and the
  mascot overlay (`src/renderer/src/mascot.tsx`) each mount their own
  `StoreProvider`. They are kept in step by the `IPC.stateChanged` broadcast added
  this session. The overlay is currently **read-only** with respect to the
  persisted slice — `mascot.tsx` carries a comment saying it must stay that way
  until the concurrent-write path is reviewed. The first feature that lets the
  overlay persist anything (drag position is the likely candidate) activates that
  work.
- **The persist guard is subtle.** `store.tsx` decides whether to write by
  string-comparing `JSON.stringify` of its slice against the last synced payload.
  That works because `sync` stores the payload's sub-objects **by reference**, so
  both sides serialize identical objects. Deep-cloning or rebuilding them on the
  sync path re-opens an unbounded write loop between the windows. Comments in
  `store.tsx` (`toSlice`) and `ipc.ts` (`saveState`) explain it.
- **Two chat backends.** `Session.tsx:59-64` picks the route from
  `settings.preferSubscription`: `/agent-sdk/chat/:agentId` (Claude subscription,
  via the Agent SDK) by default, or `/chat/:agentId` (Mastra, billed to an API
  key). The Agent SDK route calls `load()` **per request**, so agent edits apply
  immediately. The Mastra route builds agents **once at boot**
  (`startMastraServer` returns early on subsequent calls), so edits there need a
  restart — a known limitation, deliberately out of scope so far.
- **Transcripts** live in `localStorage` per session (`src/renderer/src/lib/history.ts`),
  capped at 400 messages, deliberately kept out of `settings.json`.
- **Provider keys** go through Electron `safeStorage` (DPAPI on Windows) into
  `provider-keys.bin`; the app refuses to write plaintext keys.
